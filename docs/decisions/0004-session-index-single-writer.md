# 0004 — Update the session index incrementally through one writer and bind the display with deltas

**Status**: Decided (2026-10-14), following the maintainer decisions for #616 and the review of PR #640. Implementation, performance acceptance and packaged-build qualification remain pending.

## Context

The local database must be updated in place. The display should read existing durable state and refresh only changed records; indexing must not hold terminal input. Issue #616 sets a main event-loop p99 target below **30 ms** while sessions stream, including navigation. Slices #619 and #635 moved reads/parsing into workers but left SQLite mutations on main.

The source inventory and bounded probe are in [the study](0004-session-index-study.md), especially “Main-process write inventory,” “Read and refresh graph,” and “Small isolated probe from the initial study.” Its baseline is `33e8e10f63be0c1b51062e457000683393469cac`. Decisive current paths are `session-cache.js:107` (main applies worker effects), `session-cache.js:890` (folder replacement), `main.js:1282` (Projects query/reconcile), and `public/app.js:1376` (complete display reload).

Measured in the review of PR #637 at `5053d7f`: warm main apply p99 **851 ms**, max **1,074 ms**, on 3 folders × 1,500 sessions. FTS upserts took **5.4–6.1 s** in aggregate; per-entry FTS deletes took **5.5 s**. These are prior review measurements, not a run of this ADR. PR #637 is closed, superseded by this decision. Message caps did not bound synchronous SQLite time. Its global version also rejected indexing because settings or open tabs changed, and index-dependent IPC replies waited behind a 30 s queue deadline. The merged baseline already deletes and refills whole folders at startup; #637 splits that work across observable intermediate states instead of removing it.

WAL is already enabled (`db.js:41`). There are readonly SQLite workers for Projects and search (`workers/projects-query.js:7`, `workers/search-query.js:48`). SQLite has no cross-connection row notification channel in this application; `data_version` is only a coarse indication of another connection's commits, not a change payload. See [SQLite data_version](https://www.sqlite.org/pragma.html#pragma_data_version).


## Decision

### One off-main owner for all durable writes

Use **one database file and exactly one writable connection**, owned by a long-lived Node `worker_thread` responsible for the index. Route **all** other durable writes through typed messages to it: settings, user names, stars, archive state, project/remap metadata, session/metric/continuation updates and every FTS type, including Memory and Work Files. Main holds no SQLite connection after cutover, including no readonly connection for primary-key lookups. Minimal restore/action lookups are async requests to the readonly worker; settings use the initialized mirror. Main validates IPC, owns PTYs/windows and relays committed results/events.

Keeping “small” settings/rename/archive writes on main is rejected. A one-row synchronous statement may wait up to the current **5,000 ms** busy timeout (`db.js:42`) behind another writer; rename also touches FTS (`main.js:2066`). The size of a command is not a latency bound. Moving only session FTS while file-list FTS still writes on main would violate the same contract.

Use an independent readonly display worker and the existing readonly search lane, opening separate connections to the **same** WAL file. History queries, statistics/aggregates, folder inventories, search-file-ID enumeration and display snapshots stay off main. Existing synchronous settings consumers receive an initialized in-memory settings mirror; mutations use ordered field/key commands and update that mirror on commit. Do not forward stale read/modify/write copies of the entire `global` setting: merge patches on the writer, or reject an old settings revision and retry only that command. Settings snapshots/changes use their own channel when they do not affect the sidebar.

Writer scheduling has two lanes: interactive commands and background indexing. Parse/enumerate outside write transactions, reuse filesystem parser workers for full reads, and yield between bounded parse/commit units. The writer must service commands between units rather than spend a whole scan synchronously parsing transcripts. Start with one parser, 1 MiB parsing checkpoints, and at most four interactive commands before serving pending index work; coalesce background requests by folder/file, giving explicit dirty files precedence over a full sweep. Each ordinary writer transaction, including interactive commands, admits at most **32 changed rows and 64 KiB of bound input**, whichever is reached first, with a **10 ms execution budget** excluding the separately bounded lock wait. Split FTS replacements and metric units to satisfy both limits; a larger dependency group is staged and published only when its atomic finalization fits the budget. Measure each transaction and statement. Synchronous SQL cannot be preempted: a statement over 10 ms is a ceiling violation, not an excuse to call the batch bounded. Stop further background work for that unit, reduce its admitted size or defer it for a resumable specialized path, and report the violation; acceptance must demonstrate the ceiling on the agreed fixtures. Interactive commands get priority at every transaction boundary, with the four-command fairness limit above. One-time schema migrations/VACUUM are separately reported startup/maintenance phases; they do not run alongside interactive mutations and are not claimed to meet the ordinary transaction ceiling. These are initial implementation limits to measure, not achieved timings. Readers never queue behind that mutation lane. A committed user command returns without awaiting the requested filesystem refresh; add/remap/unarchive can return `{ok:true, indexing:'pending', requestId}` after their own durable side effect. Publish later indexing success/failure separately and never report a timeout as proof that an already committed side effect failed.

Set WAL and `synchronous=NORMAL` on the writer. Use short `BEGIN IMMEDIATE` transactions, no filesystem I/O or `await` inside them, and a per-connection `busy_timeout` of **100 ms** initially. On `SQLITE_BUSY`, release the unit and retry asynchronously with bounded backoff (20/50/100 ms, then mark that unit incomplete); keep the last view and report contention. Readers use readonly/fileMustExist connections and a similarly bounded retry policy. No synchronous main fallback on a worker failure, including search. A timed-out caller gets a request ID/status path; retrying a side-effecting command uses the same deduplication token rather than applying the same mutation twice. Store command receipts/results in the same transaction as their mutations so a lost reply or writer restart does not replay the operation; bound receipt retention and return “outcome unknown” rather than replaying an expired token.

WAL permits reader/writer overlap but still serializes writes and can return BUSY. Long read transactions can pin WAL growth; use short ordinary reads and bounded snapshot leases. Run checkpoint work only off main: monitor WAL size and try PASSIVE checkpoints between jobs; reserve TRUNCATE for shutdown after readers close. Do not share this DB between application instances or over SSH/network filesystems. [SQLite WAL](https://www.sqlite.org/wal.html) defines these limits; busy timeout is a connection option, not a throughput guarantee ([better-sqlite3 API](https://github.com/WiseLibs/better-sqlite3/blob/master/docs/api.md)).

### Native loading, migrations and shutdown are part of ownership

Use `node:worker_threads`, not renderer Web Workers. `better-sqlite3` documents opening a connection inside a worker ([worker example](https://github.com/WiseLibs/better-sqlite3/blob/master/docs/threads.md)). `better-sqlite3` already runs in worker threads in packaged builds: search since **v0.0.44**, Projects since **v0.0.93**. The shipped readers open their own connections (`workers/search-query.js:48`, `workers/projects-query.js:7`). Today's worker paths use `__dirname`; packaging includes `workers/**/*` (`package.json:79`) and `asarUnpack` covers `node_modules/better-sqlite3/**` (`package.json:85`). Native install/rebuild is in `scripts/postinstall.js:8` and `scripts/postinstall.js:14`. The study's isolated 200-row probe also committed a worker transaction under Electron **41.0.3**, embedded Node **v24.14.0**, ABI **145**. Thread/native loading is an established mechanism; the new qualification concerns writable ownership and lifecycle.

Before shipping the writer, run an **installed packaged-build** smoke on each supported OS/architecture: launch through the normal Electron lifecycle with an isolated data directory, commit/read back **writes**, run fixture **migrations and VACUUM inside the writer**, and verify **awaited shutdown** and close/restart recovery. Exercise the new writer path in ASAR; do not make generic readonly worker loading the unproven premise. Rebuild only in packaging isolation, never in modules a running instance has loaded. Electron's ABI requirements still apply ([native modules](https://www.electronjs.org/docs/latest/tutorial/using-native-node-modules)); its renderer Web Worker caveats are not a reason to enable `nodeIntegrationInWorker` for this main-process worker design.

Split connection/schema setup from the current side-effectful `require('./db')`. The writer alone creates/migrates schema, reconciles columns, performs historical repairs and sets the schema version before sending `ready`. Reader workers open only afterward. Add source-signature/content-completeness and commit-version tables additively; existing rows remain readable, and absent signatures mean “needs validation.” Do not delete the database, clear all cached sessions or VACUUM at every startup. Preserve `session_meta`, settings, names and archive records through repairs; isolate any future incompatible FTS rebuild as a versioned, resumable search-only migration. Future `session_cache` columns must **never set `mustReindex`**: the existing reconciliation block (`db.js:307`, `db.js:349`) can otherwise clear all rows. Add columns with readable defaults and mark affected sources **needs validation**, scheduling resumable background work while keeping the old view. Historical destructive migrations remain explicitly versioned upgrade work; no new column inherits their cache-clearing mechanism.

Create the window shell before DB bootstrap; schema upgrades can delay DB availability, but must not freeze main. Shutdown uses one idempotent coordinator, preserving the existing exit-flush contract (#479, `public/app.js:255`), activity flush (`main.js:3612`) and final bounds save (`main.js:424`):

1. After unsaved-work consent, stop watcher/remote/index intake and background scheduling. Keep the writer accepting final lifecycle commands. Request and await renderer `exit-flush` so the working set is captured before PTY exits can empty it; retain its existing grace/error behavior.
2. Flush activity with the existing **1,500 ms** bound (`main.js:3615`). Capture final bounds before the window is destroyed; patch `windowBounds` and `openWorkingSet` as separate ordered keys, preserving both. Await their writer acknowledgements and outstanding accepted settings commands.
3. Only then reject new mutations, freeze live producers, cancel uncommitted parsing and drain already accepted commands/current transaction. Close and await display/search readers, then ask the writer to checkpoint/close and await its exit before `will-quit` finishes. PTY termination must not overwrite the saved working set.

Use a **2 s DB drain deadline**, starting after exit-flush/activity/bounds capture, rather than cutting those earlier phases off with the DB timer. Earlier phases retain their own bounded grace/deadlines; final command acknowledgements use the command timeout/status contract, reporting unknown outcomes instead of waiting indefinitely. Prevent quit only while coordinating these bounded phases; surface incomplete persistence/checkpoint on deadline. If forced termination is necessary, terminate only the worker owned by this application and await it. Committed WAL state survives; uncommitted units replay at next startup. Never depend on unawaited `terminate()` before `closeDb()` as today (`main.js:3651`), and never replace/remove WAL files manually.

On writer failure, keep the last display and notify the UI that persistence is unavailable. Do not accept new mutations until readiness returns; roll back new optimistic edits with a notice. Retain already accepted commands with their original request tokens, query their durable receipts after restart, and resend only commands proven uncommitted. Unknown/expired receipts stay unresolved with a status notice, never silently replayed. Restart with **100/500/1,000 ms** backoff and at most **three restarts in 60 s**; a fourth failure opens the circuit until explicit retry/restart. Restart creates a new epoch and forces display resync. There is no main-thread DB fallback.

### Update sessions and search only when their sources change

Keep canonical rows keyed by the existing `sessionId`. Add a source manifest keyed by `(host/folder key, relative transcript path)` with logical ID membership, file **size + high-resolution mtime**, optional file identity, parser/schema version and content-read progress. Preserve a distinct signature for fully indexed content/metrics; a header-only update must not claim that full search content is current. `fileMtime` already exists, whereas `modified` is a display timestamp (`session-cache.js:305`); `folder-index-state.js:4` is a rescan hint, not sufficient deletion evidence.

For startup, manual rescan and watcher work use the same algorithm:

1. Enumerate/stat sources in the worker. If signature and parser version are equal and complete, do not open the transcript or write its cache/FTS/metrics again. Persist successful folder progress so restart resumes without replaying completed writes. Missing signatures cause one background validation pass, not clearing the old view.
2. Parse only new/dirty sources; retain targeted watcher paths rather than reading an entire cached folder for every append. Maintain source-to-logical-ID and bridge/continuation dependencies. A changed bridge member can require rederiving affected logical siblings even when their individual file signatures stayed equal. Reuse bounded header/continuation parsing and verified cwd/remap rules; never promote an incomplete negative header result to a destructive clear.
3. Upsert changed durable display fields; update only changed FTS titles/bodies and affected daily metrics. Cache row, content/FTS, metric changes and their source signature advance atomically for a completed unit. Keep star/archive independent of parser updates and resolve the two name sources by their stored event times as decided below. Preserve FTS external-content delete ordering (`db.js:671`, `db.js:698`, `db.js:743`) and the DB ceiling of **32,768 UTF-16 code units**. Session parsing already limits the body to roughly **8 KB** of text (`read-session-file.js:309`, up to 500 units of final-append overshoot); keep that effective cap too. Compare indexed content signatures or bounded-field hashes before rewriting FTS. No delete/reinsert for an unchanged row.
4. For active transcripts, read appended bytes **incrementally from a saved byte offset every few seconds** (initial scheduling interval **2 s**, to measure before choosing a freshness target). Persist the offset, source generation, incomplete final-line bytes and parser/UUID progress with the resulting cache/search/metric update. Decode UTF-8 across chunk boundaries and advance only over complete successfully parsed records; an incomplete tail remains pending. Run bounded tail units off main, yielding to commands. Coalesce header-only `modified`/`fileMtime` writes per source to **one every 2 s**; exit drains the final tail/header unit. Re-read from byte zero only for initial validation/new files, explicit validation, shrink/size regression, or file replacement/identity change (inode or platform file ID). A failed unit keeps the old committed progress/content and stays dirty. There is **no recurring 5 s full-content read or promised 5 s freshness target**. Measure tail throughput, visible lag and transaction costs first.
5. After a **successful complete directory listing**, delete only logical rows whose last source is absent, with a stat/generation recheck before commit. Inaccessible directories, incomplete parsing, remote disconnection and partial listings are not deletion evidence. Targeted file disappearance can remove its known source after confirmed absence, not other rows. Upsert valid replacements before removing obsolete logical IDs in the same transaction where they represent one logical transition. Never empty/refill an existing folder.
6. Folder-level bulk deletion is reserved for a **confirmed vanished folder**. Removing a project from the display hides it through metadata; it does not clear the folder cache. Invalid cwd evidence quarantines the affected sources/rows and excludes unsafe display/action paths without using bulk folder deletion as a routine repair. Persist only changed folder metadata. Background project-path validation must also detect missing/remapped project directories and empty projects even when transcript signatures are unchanged; the readonly display worker never discovers those facts by mutating metadata.

Tail metrics must preserve the bridge group's **UUID union**, not count copied messages twice (`.ai/contexts/session-cache.md:138`). Persist a per-group UUID-to-contribution ledger (and daily/model buckets) **only for bridge groups with more than one member**. Ordinary single-source sessions keep tail offsets and aggregate buckets without a UUID ledger. On promotion to a multi-member group, build retained per-source UUID facts in bounded units before publishing union metrics; on return to one member, retain the surviving aggregates/progress and retire the ledger. An appended UUID already represented in the group adds no count/tokens; a new UUID adds its message/tool/token contribution once. New members, membership changes, replacement and source removal recompute ownership/contributions from those facts in bounded units; removing an owner transfers a surviving duplicate's contribution instead of subtracting it twice. Update affected rows, metrics and group revisions atomically with tail progress. For sizing, provision roughly **128–256 bytes per retained source/UUID fact**, including references and bounded contribution fields: 100,000 facts across two members imply about **12–24 MiB of logical payload**, before SQLite page/index/WAL overhead. This is an estimate, not measured storage; measure group cardinalities and on-disk overhead during acceptance. Legacy records without UUID coverage keep the existing signature/timestamp compatibility policy, explicitly flagged as approximate; never claim exact dedupe for them. Tests cover copied tails, overlapping dates, repeated delivery, restart, deletion of the previous UUID owner and one-to-many/many-to-one membership changes.

Stat equality cannot detect a same-size, timestamp-preserving rewrite. Watcher invalidation forces validation even if the stat tuple matches; an explicit deep validation command may hash/reparse content and is the named exception to “unchanged files are never reread.” Routine rescans remain stat-based. Keep local/remote folder namespaces and legacy subagent layouts; the current globally unique session-ID schema needs explicit collision fixtures before any change to identity across hosts.

### Scoped consistency instead of whole-scan conflicts

Replace the `total_changes + data_version + JSON(activeSessions)` guard with row/source revisions. A parsed result carries its observed source signature, parser version and relevant dependency revisions. Immediately before committing, stat it again; reject/requeue **only** that source or bridge group if it moved, keeping the prior row. A confirmed deletion also checks the completed listing generation and current source absence. Two failed validations mark the unit dirty for the next pass and continue other folders; unrelated settings and tab changes never restart a scan.

The writer serializes durable commands; per-field revisions and timestamped name candidates prevent stale parser results replacing newer names/archive/settings. Maintain per-folder scan generation only for membership/deletion and parser progress. Persist incomplete units and complete generations; retries resume there. Live retention is an explicit in-memory lease for the affected session, updated in order by main before its worker requests. Protect visible running rows from deletion as today (`session-cache.js:120`); revalidate that session on lease release, without treating every live change as a global database conflict. Open/exit overlays appear immediately even if an index transaction is in flight.

### Name precedence, optimistic commands and continuation metadata

**The latest rename wins**, whether it comes from Switchboard or CLI `/rename`. Keep separate candidates with `value`, `source`, `eventTime`, time provenance and source revision. Switchboard records the rename time in UTC with the value when the command is created, and the writer persists both; retry retains that time/token. CLI `custom-title` records carry `customTitle` and `sessionId` but have no timestamp in the local sample ([study evidence](0004-session-index-study.md#cli-title-record-structure)). A CLI rename event is a **change of value against the previous `custom-title` record in that same transcript**, including a return to an earlier value; identical repeated records are not events. The first title establishes a baseline when no previous value is known. Today's parser keeps only the last title (`read-session-file.js:272`); extend it to retain change offsets, preceding title value and timing context, across tail chunks and restarts.

For a local CLI value change first seen live by the tail reader **past its committed watermark**, use its **local first-observation time**, accurate to the tail interval (initially 2 s). Record that observation with pending tail work so retry/restart cannot give an already-seen change a newer time. For historical changes, use the first timestamped record **after** the change (the `local_command` when it immediately follows a `/rename`), and the nearest timestamped record **before** it only as a last resort. History with no timestamped neighbor keeps unknown time. A preceding record may belong to a turn hours before an idle-session `/rename`; it must not take precedence over live observation or following-record evidence. These are timing proxies, not a timestamp supplied by `/rename`; file mtime and identical title re-appends never date a rename. For remote hosts, compare newly observed CLI changes with Switchboard commands and other hosts by **local first-observation time**, not remote transcript timestamps, because host clocks can drift. Accept an ordering-inversion window equal to the mirror refresh interval: **300 s by default, 60 s minimum** (`remote-hosts.js:8–9`, `remote-hosts.js:54`). A remote CLI change made before a Switchboard rename can be observed afterward and win within that window. This is a trade-off during healthy periodic mirroring, not a lag bound during disconnection or refresh failure; watch/manual refresh can shorten it. Remote history discovered during migration is still a baseline, not a newly observed rename.

Persist the latest changed-value candidate per source in transcript generation/offset order, rejecting stale source revisions. Across candidates select the newer known event time. Equal times retain the previous winner; with no previous winner, use Switchboard as the deterministic tie-break. Successive changes within the same transcript are ordered by their change offsets even if their timing proxy is equal. Persist the chosen time/provenance and update the selected name and FTS title together. Re-reading a change or a repeated title cannot overwrite a newer rename.

Migration preserves `session_meta.name` without inventing history. Validate the existing transcript's title-value sequence and collapse identical repeats. If the saved name equals the current `customTitle`, classify it CLI-owned and retain the last actual change's neighboring-record time when available; a first-title-only baseline or history with no timestamped neighbor keeps **unknown time**. Otherwise classify the saved name Switchboard-owned with unknown time. Remote historical CLI candidates also keep unknown time because their local observation history is unavailable. Keep the existing name visible until classification completes.

Atomically save each transcript's generation, processed byte watermark, last title value, last **change-of-value** offset and its known/unknown time. The byte cursor may advance over identical repeats, but the rename watermark/time does not. Already-present title changes, repeated appends and rescans never defeat an unknown-time legacy name or acquire a migration observation time. **A CLI change appended between the last full scan and migration counts as baseline and does not beat a legacy Switchboard name**; accept this one-time edge case rather than inventing an observation history. Only a newly observed **value change beyond the baseline watermark** can do so, using the timing policy above; a new Switchboard command uses its actual creation time. Persist candidate/watermark advancement with the title/FTS update. Replacement or shrink requires revalidation of the baseline rather than treating replayed title history as fresh renames; retries and restarts retain the committed baseline and first-observation evidence.

**Required name-precedence tests (slice 2):** a session idle since **09:00**, renamed in Switchboard at **10:00**, then by CLI `/rename` at **11:00**, must select the CLI name. Cover both a live tail observation at 11:00 (within the tail interval) and historical reconstruction with the first timestamped record after the change, a `system`/`local_command` record at 11:00, rather than the preceding 09:00 record. Also cover a change followed first by a timestamped `assistant` record, with a `local_command` minutes later: date the change by the `assistant` record. Cover the preceding-only fallback, unknown-time history and retry/restart retaining the first observation. For remote mirroring, a CLI change at **10:00:10**, a Switchboard rename at **10:00:20** and first mirror observation at **10:05:00** deliberately select CLI under the accepted default 300 s inversion window; repeat with observation at **10:01:00** for the 60 s minimum interval, and ensure identical titles/replays do not advance that observation time. A CLI change appended after the last full scan but before migration must remain baseline and preserve the legacy Switchboard name; a later changed value beyond the baseline watermark may win.

Rename, star and archive show **immediately in the renderer store** as per-field optimistic overlays over the committed base. Send `renameSession(value, eventTime, requestId)`, `setStarred(value, requestId)` and `setArchived(value, requestId)`; star/archive are idempotent **set-value commands, never toggles**. Each overlay tracks its token/local field revision. A committed delta updates the base and reconciles the matching overlay with the final timestamp-resolved name/value; a delayed acknowledgement cannot clear a newer edit. On proven writer rejection/failure, remove only that overlay, reveal the latest committed base and show a notice. Lost replies are unknown outcomes resolved through receipts, not compensating writes. A writer outage rolls back unaccepted edits with its notice; subsequent accepted edits remain pending until their own result arrives.

Issue #639 requires `migrateUserMetadata(oldId, newId, proofRevision, requestId)`, triggered **only by a proven `continued-in` re-key**, never a fork, `/clear` or filename proximity. The existing transition path proves ownership before re-key (`session-transitions.js:464`, `session-transitions.js:487`); main revalidates that proof/session generation before accepting the command. In one writer transaction migrate **name candidates/times/provenance, star and archive**, retire old-ID metadata/membership, upsert the new canonical row, patch FTS title and persist the receipt. If new-ID metadata exists, retain explicitly set fields that are newer and fill unset fields from the old ID; add per-field times/revisions for this merge, avoiding boolean OR that undoes an explicit unstar/unarchive. Slice 2 publishes the result through today's Projects reload and transition notifications; in slice 3b the same atomic result becomes **one logical envelope with old removal and new upsert**. Surviving physical sources remain in the manifest. Move pending overlays/tokens and working-set references to the new ID without a duplicate UI row. **Unread/response-ready is renderer memory**, transferred by the existing activity re-key (`public/session-activity.js:147`, `public/session-activity.js:173`), never by this writer command. Duplicate commands read their receipt; stale proof/conflicting live ownership rejects the entire move.

### Display projection belongs to the readonly display worker

The **readonly display worker** owns the pure display projection from durable rows/settings/project facts plus versioned live inputs. It maintains durable row/membership indexes, applies changed IDs, and reprojects affected sessions, bridge/parent groups and projects. The writer produces committed durable changes and performs archive reappearance mutations. Main serializes/relays inputs/events; the renderer holds the committed projected store and optimistic/pending overlays, then patches views. Aggregation, SDK filtering and descriptor merging stay off main without persisting activity.

Port `buildProjectsFromCache` behavior: SDK retention through `activeSessions` and `global.openWorkingSet` (`session-cache.js:588`), plain terminals (`session-cache.js:766`), local background descriptors/attached jobs and merge (`session-cache.js:793`, `session-cache.js:803`), remote descriptors/`remoteAttachable` (`main.js:631`, `main.js:660`), placeholders, archive/parent hiding and bridge grouping. Main's archive planner also calls this builder (`main.js:912`); use an async projection query stamped with live revision, then revalidate action ownership on main and affected durable revisions on the writer. Remove filesystem backfills from projection: the writer publishes validated missing/remap/empty-project facts. Durable input rows below never store the projected live fields.

Main sends an initial live-input snapshot and ordered **live revision** patches for attach/exit/re-key, SDK reveal, working-set changes, local descriptors/job roster, remote descriptor/profile/attachability and plain-terminal open/exit. Existing reload signals (`main.js:2931`, `main.js:3194`, `main.js:3271`, `session-cache.js:582`) become patches even without a DB mutation. The worker reprojects affected IDs/project keys and emits projected deltas stamped with **durable epoch/sequence and live revision**. Live-only patches advance only live revision; they never conflict with indexing. Subscribe before capturing both inputs and replay queued patches from that live revision. Bound main's live-input replay buffer to **1,024 patches or 8 MiB**, whichever comes first, and each consumer's pending live bytes to 8 MiB. Overflow discards that consumer's partial live replay and replaces it with a **full current live-input snapshot** at revision `L`, capturing/subscribing in one ordered main turn and replaying only patches after `L`. Keep the last installed view until the replacement is complete; epoch changes also require durable resync. Apply the same one-in-flight / one-per-2-s recovery limit as durable resync. Busy/task/transcript channels stay separate. Global visibility changes may touch many rows in bounded chunks but cause no history query/full `get-projects` reload. This transport contract lands in 3b; 3a checks the projection with in-process change sets.

**Parity reference:** fixture DB rows/settings/folder facts plus identical captured live inputs. In **slice 3a**, compare the initial snapshot and the result after **each in-process durable/live change set** against current `buildProjectsFromCache(false/true)`, including placeholder/archive assembly, remote annotation and the archive-planner consumer. These fixtures call the projection directly; they require no transport, epoch or sequence. Stub filesystem facts deterministically; canonicalize only incidental array order, not grouping/visibility. Cover SDK rows retained by tabs, merged non-SDK children, plain/panel terminals, attached background rows and renamed descriptors, empty/hidden/archived projects, remote bridge-head attachability, descriptor-only changes and proven continuation metadata transfer. Comparing the new projection only with itself proves no parity. **Slice 3b** then verifies the same ordered changes through transport and recovery.

### Publish ordered committed deltas

Use an explicit writer → readonly display worker → main → preload → renderer stream for projected changes. In slice 3b, create a **`MessageChannel` between writer and display worker**, transferring one port to each, so durable payloads do not cross main on both sides of projection. Main owns channel setup/restart, relays versioned live inputs and control requests, and forwards projected output without evaluating the projection. Direct-port acknowledgements/backpressure use the same bounded protocol below; a broken port triggers recovery, never a second main relay publishing duplicate deltas. Read workers are pure readers: reconciliation moves to the writer, and `get-projects` no longer has archive/settings side effects. The writer increments a durable **commit sequence** in the same transaction as its durable mutation. A writer startup also creates a fresh in-memory **epoch**; restarting the writer requires a new display snapshot even if the sequence happened to survive unchanged.

The writer's logical durable-input envelope is:

```text
{
  epoch, fromSeq, toSeq,
  folders: [{
    folder, project: <changed project metadata or absent>,
    upserted: [<complete durable display rows>], removed: [<sessionId>],
    removedProject: <boolean>
  }]
}
```

Rows include `sessionId`, folder/host identity, project path, display timestamps, counts, titles/name, star/archive, parent/bridge/merged membership and relevant durable visibility fields. Exclude transcript bodies, continuation indexes and live activity/task state. Project changes include empty projects, missing/hidden/archive state and offers needed by the UI; a move/bridge operation includes old membership removal and all affected parents. Apply membership removals before installing all final upserts across the entire envelope; delete a canonical row only when it has no final membership/upsert. A move's removal from its old folder must never erase its new row because the folders arrived in a different order. These inputs let the readonly worker preserve default/archived/search views without transferring duplicate full arrays. `upserted` contains full replacement display records, not ambiguous partial field merges. Ordinary settings/FTS-only commits may advance the sequence with an empty display delta; never silently create a sequence gap.

Emit only after commit. Sequence is global within the DB, not a separate counter per folder. Coalesce contiguous commits for up to **100 ms**; merge successive updates by ID with last operation winning, preserve folder moves and all removals, and send `fromSeq` equal to the previously covered version. For durable inputs, a receiver at `toSeq` ignores duplicates; one at `fromSeq` applies atomically; any other version/epoch requests resync. Projected output additionally carries `fromLiveRev`/`toLiveRev`: compare both version lanes, so a live-only envelope at the same durable sequence is applied, not mistaken for a duplicate. Advance the pair only after all parts arrive. The renderer never infers order from wall-clock timestamps.

Use acknowledged backpressure and an initial **200-row / 128 KiB** transport cap, with at most two unacknowledged frames per consumer at each hop. These cap transport costs, not SQL time. Larger logical deltas use numbered parts with the same version interval; the receiver stages them and advances its version only after all parts arrive. Cap projected string fields and load oversized detail separately. Buffer and acknowledgement ownership follows the direct channel:

- **Writer → display worker:** the writer owns the constituent-commit replay ring (**1,024 commits or 8 MiB**, whichever first), including commits coalesced into transport frames, and the direct port's unacknowledged frames. The display worker owns inbound part staging, bounded to 8 MiB, and sends frame acknowledgements directly to the writer after bounded staging; its installed durable-sequence acknowledgement advances only after the complete interval is applied. These acknowledgements do not wait for main or any renderer. Ring eviction or an input gap requires display-worker recovery; a slow renderer never stalls the writer.
- **Display worker → main:** the display worker owns each renderer consumer's projected-output backlog, dirty-ID/project-key set and recovery high-water pair, bounded to 8 MiB per consumer. Main owns only the bounded relay frames and per-window acknowledgement tracking, with the same two-frame/8 MiB ceiling, and performs no projection or database recovery reads. Main acknowledges receipt after accepting a frame into its bounded relay; this frees the display-to-main transport slot, but does not acknowledge renderer installation. If forwarding backs up, main signals that consumer's lag to the display worker, which collapses its pending output to dirty IDs/project keys rather than continuing to queue payloads.
- **Main → renderer:** the renderer owns bounded part staging (8 MiB) and its installed store/version pair. It acknowledges each frame to main after staging, and acknowledges installation of the durable/live pair only after the entire interval is applied atomically. Main forwards those acknowledgements to the display worker for that consumer; only the installation acknowledgement advances its installed pair. Receipt acknowledgements at earlier hops cannot retire that consumer's recovery state. Missing acknowledgements trigger the existing timeout/resync path.

For a backlogged renderer, the **display worker** collapses superseded updates to its consumer's dirty-ID/project-key set, retaining removals/move dependencies and the latest high-water sequence/live revision. It recovers by re-reading only those IDs/dependencies through its readonly connection in one versioned transaction, projects with the latest live revision, and emits an explicit replacement interval through main. Confirmed absent IDs become removals. If the set exceeds its ceiling or the base epoch is unknown, discard it and request a snapshot. Rate-limit recovery/resync to **one attempt per consumer per 2 s**, with at most one in flight; coalesce further requests while preserving the last view/progress. Replacement intervals are marked as recovery, never passed off as contiguous replay. Slow/hidden windows never stall the writer or accumulate unbounded data. Empty intervals may use compact sequence ranges in the writer's ring and be split at any requested version.

On reload, missed part, gap, timeout or epoch change: subscribe/buffer durable inputs at the display worker's writer port and live inputs/output at main **before** requesting a readonly snapshot. The read worker obtains display rows, project/visibility metadata and durable sequence `S` in **one read transaction**. The display worker installs the durable snapshot with its captured live revision and projects it; main relays its chunks for renderer installation. Drop covered durable events, request `replayAfter(epoch, S)` from the writer through main's control path, and apply the contiguous suffix over the direct port in the display worker before projecting further renderer deltas. Replay live-input patches from the captured live revision independently; live-buffer overflow uses the full-live-snapshot replacement above. A snapshot can split a transported coalesced interval: for `S=10` and buffered `(9,11]`, rebuild `(10,11]` from retained commit 11; never feed the overlapping envelope to the exact-version receiver or repeatedly resnapshot just because of coalescing. Replay capture registers its consumer at its high-water sequence before live delivery continues, so the replay/live boundary has no gap. If constituent history no longer covers `S`, resnapshot. A normal reload within replay retention may request only the suffix. A writer crash after DB commit but before emission is repaired by epoch reset/snapshot, not by guessing which event was sent. No durable event log is required initially.

### Bind the display to a store and patch only affected views

The renderer keeps a committed projected `Map<sessionId, row>` and project/folder indexes, initialized by the display worker snapshot. Archived/default/search presentations use that store with synthetic pending rows, optimistic command overlays and activity channels. Plain-terminal membership and descriptor/SDK policy are projected by the display worker, avoiding duplicate policy owners. Preserve existing archive reappearance, parent/subagent hiding, SDK filtering, remap trust, remote attachability and worktree nesting policies. Writer-owned archive reappearance runs as reconciliation, not as a query side effect.

After each delta update the affected IDs, related parent/bridge aggregates and project counts, then patch only the touched visible DOM nodes/groups. Schedule bounded work per frame (initial **10 ms** budget, instrumented); preserve terminal focus, selection, stable order and retained object identity. Do not call today's whole-tree `refreshSidebar`/`renderProjects` after every delta. Filters or a deliberate global resort may update a broader view, but never cause a database rebuild. An ordinary durable change must issue **zero full `get-projects` calls**. Settings, ID discovery, archive/delete and background events currently forcing full reloads must instead update their store/overlay or await their versioned command result.

Snapshot reads/materialization happen in the readonly worker, never synchronously on main or in the renderer. Stream bounded chunks from the same snapshot transaction, staging installation in the renderer; release the read transaction on completion or a **2 s lease** and retry if incomplete. Main/renderer acknowledge and yield between chunks. Very large snapshots may require paginated visible-first hydration in a later revision; a snapshot that repeatedly exceeds the lease must show a recoverable indexing/view error rather than hold a transaction forever. It does not delay working-set restore.

The initial study's 200-row probe found `SELECT *` mean **0.370 ms**, max **1.045 ms**, **113,273** JSON bytes; a six-column projection mean **0.149 ms**, max **0.188 ms**, **33,583** bytes. This is an illustrative lower-bound fixture: no real histories, locks, FTS, DOM or IPC serialization, and it omits fields the actual display needs. It justifies explicit projections and off-main reads, **not** a safe history size on main. Measure actual structured-clone and renderer costs; splitting SQLite connections alone does not satisfy #616.

### Keep live state on its current channels

Persist projects, indexed sessions/subagents, titles/names, user star/archive/settings, search and historical metrics. Keep busy spinner/turn, unread/response-ready, running subagent sets, task registry, transcript activity, attention and PTY ownership in memory, on their existing channels. Unread follows the renderer activity re-key and is not durable metadata. Reconstruct live state from its existing observations after restart; a durable historical subagent row is not evidence that the subagent is running.

The source-derived rates support that boundary: local transcript activity allows one IPC per session per **1 s** (`local-transcript-activity.js:9`), PTY state polls at **3 s** running / **30 s** idle (`public/app.js:1190`), and busy/terminal/task events are event-driven. For ten active sessions, persisting every allowed transcript heartbeat alone could add about **10 writes/s** without a durable-data change; that is a rate envelope, not a measured workload. Durable unchanged files produce **zero** indexing writes; user actions are discrete commands. Persisting each spinner/attention transition would both couple UI liveness to disk and reintroduce unrelated invalidations.

### Startup is stale-while-revalidate

Show the window shell immediately; after schema readiness, fetch settings/working-set records and a readonly display snapshot independently of background indexing. Paint the last durable snapshot with a validating indicator, then stream deltas. Empty or interrupted caches show project placeholders/progress while preserving pending and restored rows. Begin working-set restore as soon as its settings and minimal session lookups are available; never await full snapshot hydration, directory validation, search refresh or a full-scan queue. Keep existing live-elsewhere/continuation guards.

Set an initial engineering budget of **first cached sidebar paint within 500 ms after writer schema readiness** on the agreed warm fixture, and a provisional **250 ms command acknowledgement** target while indexing. These are proposed budgets, not measurements or substitutes for #616's p99 **<30 ms** and no input-hold acceptance. A long one-time schema upgrade displays progress/error on the responsive shell; it cannot be hidden inside a startup main-thread import.

## Consequences

### Migration in four reviewable slices

1. **Connection ownership and lifecycle**, split into independently reviewable changes:
   - **1a — async facade, still on main.** Route every write in the study through a typed async facade, still backed by the existing main-owned connection. Await commands at their callers and preserve ordering, error/IPC semantics, scan results, title behavior and full reloads. No worker cutover or new product behavior; this is a pure refactor. Characterize every direct/injected writer, including file-list FTS, settings and lifecycle writes. Explicitly inventory main-side read-then-write sequences: rename's metadata/cache read/FTS patch (`main.js:2066–2072`), worktree row selection/deletion plus `global.hiddenProjects` cleanup (`main.js:1045–1063`), and archive helpers' reads of `global`/archive/offer settings followed by writes (study's command inventory). Main still has its existing writable/read connection in this temporary slice.
   - **1b — swap the facade backend to the writer.** Move schema/bootstrap and all facade writes to the worker in one cutover, initialize the settings mirror, route reads to independent readonly workers and remove main's connection, even for primary-key lookups. Each inventoried read-then-write sequence becomes **one writer command**, reading current state and applying its durable changes in one transaction; never split it into a readonly-worker lookup followed by a stale write. Filesystem/schedule side effects stay outside the transaction with explicit completion commands. Preserve the old indexing/display behavior temporarily, but remove query-side writes from reader requests. Add receipt recovery, migrations, writer restart/lock/error paths and the coordinated awaited shutdown; qualify packaged writes/migrations/VACUUM/shutdown. No mixed-writer phase or synchronous fallback.
2. **Incremental sources and consistency.** Add source signatures/tail progress, UUID-deduped changed-only metrics/search, changed-value name migration/precedence with timing provenance, idempotent set commands, the proven-continuation metadata command, confirmed missing-ID deletion, live leases and folder progress. Replace global invalidation with scoped checks. Move `detectSessionTransitions`' synchronous enumeration/header/continuation/subagent reads (`main.js:3309`, `session-transitions.js:395`, `session-transitions.js:501`) into bounded parser work with saved tail state; keep final live ownership/PTY re-key decisions on main, checking the observed session generation after the async result and before the writer metadata command. Preserve transition ordering before folder updates and descriptor ownership checks. Validate warm no-op, changed/new/deleted files, unavailable folders, incomplete tails/UTF-8, replacement/shrink, bridge UUID ownership changes, concurrent/replayed renames, metadata re-key and restart of incomplete work. Avoid large/live runs in this documentation revision; qualification belongs to the acceptance owner.
   Slice 2 publishes changed results, including continuation metadata transfer, through today's Projects reload/transition notifications; it does not depend on slice 3b's envelopes or sequence machinery.
3. **Snapshot/delta backend**, split into explicit sub-slices:
   - **3a — pure display projection port and parity.** Extract the pure projection into the readonly display worker and route live snapshots and archive-planner queries through it, retaining full reload publication. Prove initial-snapshot and **in-process change-set** parity against the existing `buildProjectsFromCache` pipeline on the fixtures above, without transport, epochs or sequences. No hidden duplicate main/renderer policy.
   - **3b — committed delta transport and recovery.** Add the writer/display `MessageChannel`, durable sequence/epoch, versioned live-input patches, coalescing, bounded durable/live replay, dirty-ID backpressure and rate-limited resync/chunk acknowledgements. Test snapshot races (including `S=10` inside `(9,11]`), replay/live high-water boundaries, live-buffer overflow/full-live-snapshot replacement, gaps/duplicates/parts, empty commits, moves/removal, writer death after commit, port replacement and slow-consumer bounds. Keep the old renderer compatible temporarily; never enable both full reload and delta rendering for the same consumer.
4. **Renderer store and acceptance.** Switch startup/ordinary events to the store, enable optimistic rename/star/archive reconciliation/rollback, patch affected DOM/groups, separate restore from indexing/hydration, and remove obsolete full reload/effect routes. Test pending/plain terminals, archive/search/SDK/remote/subagent/bridge policies, retained focus/order, stale command replies, and zero full reloads for a single-row or live-descriptor change. Capture main p99/max, relay/render task time, transaction ceilings, snapshot bytes/paint, tail lag, command latency, WAL growth and observed typing with streaming sessions/navigation.

**Full Projects reloads remain until slice 4. Typing acceptance lands only with slice 4**, when the remaining main transition reads and full renderer rebuilds are gone. Slices 1b and 2 reduce known main costs but do not claim #616 acceptance. Acceptance requires main p99 **<30 ms and no observed input hold**, not merely a small probe or green unit suite. For the main-loop histogram measurement, start with `SWITCHBOARD_MAIN_LOOP_HISTOGRAM=1` and tracing enabled: `main.loop.p99Ms`/`maxMs` then use a 20 ms resolution with an idle floor of at least 20 ms. Ordinary `lagMs` samples do not establish the p99 target.

**PR #637 is closed, superseded by this ADR; do not merge its architecture.** Reusable parts remain: selected source-reading helpers, transition parsing and regression fixtures after comparison with the merged baseline; `workers/index-sessions.js` for per-folder job/backfill enumeration after removing its readonly-effect adapter, whole-folder clearing and global retries; `index-effect-batches.js` for byte framing, never as a SQL time bound or command protocol. Preserve correct watcher transition ordering/ownership and IPC semantics. Exclude the appended FTS SQL defect and weakened tests. This records the completed PR disposition, not a request to close it.

### Risks and rejected alternatives

| Risk / alternative | Disposition |
| --- | --- |
| Time-sliced main-applied batches | Rejected as the target design: one FTS statement or lock wait is not preemptible, and 50 effects/128 KiB already failed measured latency. May reduce symptoms during an isolated emergency, but cannot establish this ownership contract. |
| Worker owns index writes, main keeps “small” writes | Rejected: two writers still contend and synchronous lock waiting still holds all main IPC. |
| One copied database per reader | Rejected: redundant writes, lagging copies and no shared transaction/version boundary. Multiple readonly **connections** to one WAL DB are the chosen design. |
| In-memory-only index | Rejected: loses stale-while-revalidate startup and makes every restart depend on a full history scan; durable user metadata still needs storage. |
| Poll `data_version` and reload all projects | Rejected for normal updates: no row identities, invalidates on unrelated writes and recreates whole-history/display costs. A full snapshot is a recovery tool. |
| Full atomic folder rebuild | Rejected for ordinary refresh: rewrites unchanged FTS, long transactions, poor command fairness. Commit changed source/dependency units atomically; only disappearance permits bulk folder deletion. |
| Single worker for parsing, writes, search and snapshots | Rejected: full reads/FTS would queue interactive reads behind indexing. Separate read lanes and interruptible parser work are required. |
| Off-main work still saturates CPU/disk | Limit parser concurrency and background throughput; measure typing, reader latency and WAL checkpoints. Moving threads is necessary but not sufficient. |
| Delta projection misses an indirect effect | Include parent/bridge membership, hidden/archive settings and empty projects; 3a parity fixtures compare snapshots and in-process durable/live change sets against the existing `buildProjectsFromCache` pipeline and its assembly/annotation; 3b verifies transport of those changes. Force resync on protocol/version errors. |
| Native crash terminates the Electron process | Worker threads do not isolate native crashes. Packaged smoke and error paths are required; move the writer to a utility process later if observed native crashes justify that extra boundary. |
| Old schema / downgrade / persistence | Additive upgrades preserve user tables. Back up before any future destructive migration; define supported downgrade versions before releasing such migrations. No routine DB replacement. |
| Same-size/mtime rewrite, host-ID collision, unavailable remote | Forced validation for dirty events; explicit deep check for stat collisions; preserve namespace and add collision fixtures; retain cached remote data while unreachable. Do not silently declare missing files. |
| Snapshot lease repeatedly exhausted | Instrument visible size and recovery. Revisit paginated snapshot hydration without blocking restore; never use synchronous main reads as an escape hatch. |

The implementation pays for a command boundary, a renderer store and explicit replay semantics. In exchange, startup and display reads no longer mutate the index, unchanged sessions cost no reparsing/rewriting, and the UI receives bounded changes instead of rebuilding all projects on each notification. All numerical tuning budgets above remain provisional until the four slices produce acceptance evidence.
