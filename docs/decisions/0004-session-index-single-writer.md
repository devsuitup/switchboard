# 0004 — Update the session index incrementally through one writer and bind the display with deltas

**Status**: Proposed (2026-10-14); implements the maintainer's architecture direction for #616. Performance acceptance and packaged-build qualification remain pending.

## Context

The local database must be updated in place. The display should read existing durable state and refresh only changed records; indexing must not hold terminal input. Issue #616 sets a main event-loop p99 target below **30 ms** while sessions stream, including navigation. Slices #619 and #635 moved reads/parsing into workers but left SQLite mutations on main.

The source inventory and bounded probe are in [Study 6164](0004-session-index-study.md), especially “Main-process write inventory,” “Read and refresh graph,” and “Small fresh probe.” Its baseline is `33e8e10f63be0c1b51062e457000683393469cac`. Decisive current paths are `session-cache.js:107` (main applies worker effects), `session-cache.js:890` (folder replacement), `main.js:1282` (Projects query/reconcile), and `public/app.js:1376` (complete display reload).

The supplied review of PR #637 at `5053d7f` measured warm main apply p99 **851 ms**, max **1,074 ms**, on 3 folders × 1,500 sessions. FTS upserts took **5.4–6.1 s** in aggregate; per-entry FTS deletes took **5.5 s**. These are prior review measurements, not a run of this ADR. Message caps did not bound synchronous SQLite time. Its global version also rejected indexing because settings or open tabs changed, and index-dependent IPC replies waited behind a 30 s queue deadline. The merged baseline already deletes and refills whole folders at startup; #637 splits that work across observable intermediate states instead of removing it.

WAL is already enabled (`db.js:41`). There are readonly SQLite workers for Projects and search (`workers/projects-query.js:7`, `workers/search-query.js:48`). SQLite has no cross-connection row notification channel in this application; `data_version` is only a coarse indication of another connection's commits, not a change payload. See [SQLite data_version](https://www.sqlite.org/pragma.html#pragma_data_version).


## Decision

### One off-main owner for all durable writes

Use **one database file and exactly one writable connection**, owned by a long-lived Node `worker_thread` responsible for the index. Route **all** other durable writes through typed messages to it: settings, user names, stars, archive state, project/remap metadata, session/metric/continuation updates and every FTS type, including Memory and Work Files. Main holds no writable SQLite connection after cutover. It validates IPC, owns PTYs/windows and relays committed results/events.

Keeping “small” settings/rename/archive writes on main is rejected. A one-row synchronous statement may wait up to the current **5,000 ms** busy timeout (`db.js:42`) behind another writer; rename also touches FTS (`main.js:2066`). The size of a command is not a latency bound. Moving only session FTS while file-list FTS still writes on main would violate the same contract.

Use an independent readonly display worker and the existing readonly search lane, opening separate connections to the **same** WAL file. History queries, statistics/aggregates, folder inventories, search-file-ID enumeration and display snapshots stay off main. Existing synchronous settings consumers receive an initialized in-memory settings mirror; mutations use ordered field/key commands and update that mirror on commit. Do not forward stale read/modify/write copies of the entire `global` setting: merge patches on the writer, or reject an old settings revision and retry only that command. Settings snapshots/changes use their own channel when they do not affect the sidebar.

Writer scheduling has two lanes: interactive commands and background indexing. Parse/enumerate outside write transactions, reuse filesystem parser workers for full reads, and yield between bounded parse/commit units. The writer must service commands between units rather than spend a whole scan synchronously parsing transcripts. Start with one parser, 1 MiB parsing checkpoints, and at most four interactive commands before serving pending index work; coalesce background requests by folder/file, giving explicit dirty files precedence over a full sweep. These are initial implementation limits to measure, not achieved timings. Readers never queue behind that mutation lane. A committed user command returns without awaiting the requested filesystem refresh; add/remap/unarchive can return `{ok:true, indexing:'pending', requestId}` after their own durable side effect. Publish later indexing success/failure separately and never report a timeout as proof that an already committed side effect failed.

Set WAL and `synchronous=NORMAL` on the writer. Use short `BEGIN IMMEDIATE` transactions, no filesystem I/O or `await` inside them, and a per-connection `busy_timeout` of **100 ms** initially. On `SQLITE_BUSY`, release the unit and retry asynchronously with bounded backoff (20/50/100 ms, then mark that unit incomplete); keep the last view and report contention. Readers use readonly/fileMustExist connections and a similarly bounded retry policy. No synchronous main fallback on a worker failure, including search. A timed-out caller gets a request ID/status path; retrying a side-effecting command uses the same deduplication token rather than toggling a star twice. Store command receipts/results in the same transaction as their mutations so a lost reply or writer restart does not replay the operation; bound receipt retention and return “outcome unknown” rather than replaying an expired token.

WAL permits reader/writer overlap but still serializes writes and can return BUSY. Long read transactions can pin WAL growth; use short ordinary reads and bounded snapshot leases. Run checkpoint work only off main: monitor WAL size and try PASSIVE checkpoints between jobs; reserve TRUNCATE for shutdown after readers close. Do not share this DB between application instances or over SSH/network filesystems. [SQLite WAL](https://www.sqlite.org/wal.html) defines these limits; busy timeout is a connection option, not a throughput guarantee ([better-sqlite3 API](https://github.com/WiseLibs/better-sqlite3/blob/master/docs/api.md)).

### Native loading, migrations and shutdown are part of ownership

Use `node:worker_threads`, not renderer Web Workers. `better-sqlite3` documents opening a connection inside a worker ([worker example](https://github.com/WiseLibs/better-sqlite3/blob/master/docs/threads.md)). Today's worker paths use `__dirname`; the build includes `workers/**/*` and unpacks `better-sqlite3` (`package.json`, `scripts/postinstall.js:7`). A fresh isolated 200-row probe loaded the native module and committed a worker transaction under Electron **41.0.3**, embedded Node **v24.14.0**, ABI **145**. This proves the installed development dependency supports the mechanism, not that all distributables work.

Before shipping the writer, run an **installed packaged-build** smoke on each supported OS/architecture: launch through the normal Electron lifecycle with an isolated data directory, load the writer and readonly worker from the packaged paths, migrate a fixture, commit/read back, close and restart. Assert ASAR/native resolution and DB recovery. Rebuild only in packaging isolation, never in modules a running instance has loaded. Electron's ABI requirements still apply ([native modules](https://www.electronjs.org/docs/latest/tutorial/using-native-node-modules)); its renderer Web Worker caveats are not a reason to enable `nodeIntegrationInWorker` for this main-process worker design.

Split connection/schema setup from the current side-effectful `require('./db')`. The writer alone creates/migrates schema, reconciles columns, performs historical repairs and sets the schema version before sending `ready`. Reader workers open only afterward. Add source-signature/content-completeness and commit-version tables additively; existing rows remain readable, and absent signatures mean “needs validation.” Do not delete the database, clear all cached sessions or VACUUM at every startup. Preserve `session_meta`, settings, names and archive records through repairs; isolate any future incompatible FTS rebuild as a versioned, resumable search-only migration. Legacy migrations that invalidate derived data remain exceptional, explicit upgrade work, not the steady-state update algorithm.

Create the window shell before DB bootstrap; schema upgrades can delay DB availability, but must not freeze main. On shutdown: stop watcher/remote intake and reject new mutations; flush already accepted settings/working-set commands and the current transaction; cancel uncommitted parsing; close/await display and search readers; have the writer checkpoint and close; await its exit. Use a bounded shutdown deadline (initially **2 s**), prevent quit only while draining, and report an incomplete checkpoint instead of blocking indefinitely. If forced termination is necessary, terminate only the worker owned by this application; committed WAL state survives, uncommitted units replay at next startup. Never depend on calling `terminate()` without awaiting it before `closeDb()` as today (`main.js:3651`). Do not replace or remove WAL files manually.

### Update sessions and search only when their sources change

Keep canonical rows keyed by the existing `sessionId`. Add a source manifest keyed by `(host/folder key, relative transcript path)` with logical ID membership, file **size + high-resolution mtime**, optional file identity, parser/schema version and content-read progress. Preserve a distinct signature for fully indexed content/metrics; a header-only update must not claim that full search content is current. `fileMtime` already exists, whereas `modified` is a display timestamp (`session-cache.js:305`); `folder-index-state.js:4` is a rescan hint, not sufficient deletion evidence.

For startup, manual rescan and watcher work use the same algorithm:

1. Enumerate/stat sources in the worker. If signature and parser version are equal and complete, do not open the transcript or write its cache/FTS/metrics again. Persist successful folder progress so restart resumes without replaying completed writes. Missing signatures cause one background validation pass, not clearing the old view.
2. Parse only new/dirty sources; retain targeted watcher paths rather than reading an entire cached folder for every append. Maintain source-to-logical-ID and bridge/continuation dependencies. A changed bridge member can require rederiving affected logical siblings even when their individual file signatures stayed equal. Reuse bounded header/continuation parsing and verified cwd/remap rules; never promote an incomplete negative header result to a destructive clear.
3. Upsert changed durable display fields; update only changed FTS titles/bodies and affected daily metrics. Cache row, content/FTS, metric changes and their source signature advance atomically for a completed unit. Keep names/archive in separate user-owned fields so background parsing cannot overwrite a user rename. Preserve FTS external-content delete ordering (`db.js:671`, `db.js:698`, `db.js:743`) and the **32,768-character** body cap. Compare indexed content signatures or bounded-field hashes before rewriting FTS. No delete/reinsert for an unchanged row.
4. For active transcripts, promptly publish bounded header changes; queue a full-content refresh at most once per source every **5 s** while dirty and a final pass at exit. Full reads must occur off main and yield to interactive commands. Use size/tail progress to update metrics safely and detect truncation/replacement. The 5 s search/metric freshness target is proposed, not existing behavior. A failed parse leaves old complete content and its old signature, and stays dirty. This replaces today's reliance on a full startup reread to refresh live FTS/metrics.
5. After a **successful complete directory listing**, delete only logical rows whose last source is absent, with a stat/generation recheck before commit. Inaccessible directories, incomplete parsing, remote disconnection and partial listings are not deletion evidence. Targeted file disappearance can remove its known source after confirmed absence, not other rows. Upsert valid replacements before removing obsolete logical IDs in the same transaction where they represent one logical transition. Never empty/refill an existing folder.
6. Folder-level bulk deletion is reserved for a **confirmed vanished folder**. Removing a project from the display hides it through metadata; it does not clear the folder cache. Invalid cwd evidence quarantines the affected sources/rows and excludes unsafe display/action paths without using bulk folder deletion as a routine repair. Persist only changed folder metadata. Background project-path validation must also detect missing/remapped project directories and empty projects even when transcript signatures are unchanged; the readonly display worker never discovers those facts by mutating metadata.

Stat equality cannot detect a same-size, timestamp-preserving rewrite. Watcher invalidation forces validation even if the stat tuple matches; an explicit deep validation command may hash/reparse content and is the named exception to “unchanged files are never reread.” Routine rescans remain stat-based. Keep local/remote folder namespaces and legacy subagent layouts; the current globally unique session-ID schema needs explicit collision fixtures before any change to identity across hosts.

### Scoped consistency instead of whole-scan conflicts

Replace the `total_changes + data_version + JSON(activeSessions)` guard with row/source revisions. A parsed result carries its observed source signature, parser version and relevant dependency revisions. Immediately before committing, stat it again; reject/requeue **only** that source or bridge group if it moved, keeping the prior row. A confirmed deletion also checks the completed listing generation and current source absence. Two failed validations mark the unit dirty for the next pass and continue other folders; unrelated settings and tab changes never restart a scan.

The writer serializes durable commands; metadata field ownership prevents stale parser results replacing newer names/archive/settings. Maintain per-folder scan generation only for membership/deletion and parser progress. Persist incomplete units and complete generations; retries resume there. Live retention is an explicit in-memory lease for the affected session, updated in order by main before its worker requests. Protect visible running rows from deletion as today (`session-cache.js:120`); revalidate that session on lease release, without treating every live change as a global database conflict. Open/exit overlays appear immediately even if an index transaction is in flight.

### Publish ordered committed deltas

Use an explicit writer → main → preload → renderer event stream. Read workers are pure readers: reconciliation moves to the writer, and `get-projects` no longer has archive/settings side effects. The writer increments a durable **commit sequence** in the same transaction as its durable mutation. A writer startup also creates a fresh in-memory **epoch**; restarting the writer requires a new display snapshot even if the sequence happened to survive unchanged.

The logical display envelope is:

```text
{
  epoch, fromSeq, toSeq,
  folders: [{
    folder, project: <changed project metadata or absent>,
    upserted: [<complete durable display rows>], removed: [<sessionId>],
    removedProject: <boolean>
  }]
}
```

Rows include `sessionId`, folder/host identity, project path, display timestamps, counts, titles/name, star/archive, parent/bridge/merged membership and relevant durable visibility fields. Exclude transcript bodies, continuation indexes and live activity/task state. Project changes include empty projects, missing/hidden/archive state and offers needed by the UI; a move/bridge operation includes old membership removal and all affected parents. Apply membership removals before installing all final upserts across the entire envelope; delete a canonical row only when it has no final membership/upsert. A move's removal from its old folder must never erase its new row because the folders arrived in a different order. This projection preserves default/archived/search views without transferring duplicate full arrays. `upserted` contains full replacement display records, not ambiguous partial field merges. Ordinary settings/FTS-only commits may advance the sequence with an empty display delta; never silently create a sequence gap.

Emit only after commit. Sequence is global within the DB, not a separate counter per folder. Coalesce contiguous commits for up to **100 ms**; merge successive updates by ID with last operation winning, preserve folder moves and all removals, and send `fromSeq` equal to the previously covered version. A receiver at `toSeq` ignores duplicates; one at `fromSeq` applies the batch atomically; any other version/epoch requests resync. The renderer never infers order from wall-clock timestamps.

Use acknowledged backpressure and an initial **200-row / 128 KiB** transport cap, with at most two unacknowledged frames per consumer. These cap transport costs, not SQL time. Larger logical deltas use numbered parts with the same version interval; the receiver stages them and advances its version only after all parts arrive. Cap projected string fields and load oversized detail separately. The writer retains constituent commit deltas in a bounded replay ring (initially **1,024 commits or 8 MiB**, whichever first), even when transport coalesces them. Bound each consumer's pending bytes by the same byte ceiling; if exceeded, discard that consumer's backlog and send `resync-required`. Slow/hidden windows must never stall the writer or accumulate unbounded data. Empty intervals may use compact sequence ranges in the ring and be split at any requested version.

On reload, missed part, gap, timeout or epoch change: subscribe/buffer at main **before** requesting a readonly snapshot. The read worker obtains display rows, project/visibility metadata and durable sequence `S` in **one read transaction**. Main installs that snapshot, drops buffered events covered by `S`, then requests `replayAfter(epoch, S)` from the writer and replays a contiguous suffix starting at `S`. A snapshot can split a transported coalesced interval: for `S=10` and buffered `(9,11]`, rebuild `(10,11]` from retained commit 11; never feed the overlapping envelope to the exact-version receiver or repeatedly resnapshot just because of coalescing. Replay capture registers its consumer at its high-water sequence before live delivery continues, so the replay/live boundary has no gap. If constituent history no longer covers `S`, resnapshot. A normal reload within replay retention may request only the suffix. A writer crash after DB commit but before emission is repaired by epoch reset/snapshot, not by guessing which event was sent. No durable event log is required initially.

### Bind the display to a store and patch only affected views

The renderer keeps a durable `Map<sessionId, row>` plus project/folder membership indexes, initialized from the single logical DB snapshot. Archived/default/search presentations are derived views of that store; retain synthetic pending/plain-terminal rows and live channels as overlays. Preserve existing archive reappearance, parent/subagent hiding, SDK filtering, remap trust, remote attachability and worktree nesting policies. Writer-owned archive reappearance runs as reconciliation, not as a query side effect.

After each delta update the affected IDs, related parent/bridge aggregates and project counts, then patch only the touched visible DOM nodes/groups. Schedule bounded work per frame (initial **10 ms** budget, instrumented); preserve terminal focus, selection, stable order and retained object identity. Do not call today's whole-tree `refreshSidebar`/`renderProjects` after every delta. Filters or a deliberate global resort may update a broader view, but never cause a database rebuild. An ordinary durable change must issue **zero full `get-projects` calls**. Settings, ID discovery, archive/delete and background events currently forcing full reloads must instead update their store/overlay or await their versioned command result.

Snapshot reads/materialization happen in the readonly worker, never synchronously on main or in the renderer. Stream bounded chunks from the same snapshot transaction, staging installation in the renderer; release the read transaction on completion or a **2 s lease** and retry if incomplete. Main/renderer acknowledge and yield between chunks. Very large snapshots may require paginated visible-first hydration in a later revision; a snapshot that repeatedly exceeds the lease must show a recoverable indexing/view error rather than hold a transaction forever. It does not delay working-set restore.

The fresh 200-row probe found `SELECT *` mean **0.370 ms**, max **1.045 ms**, **113,273** JSON bytes; a six-column projection mean **0.149 ms**, max **0.188 ms**, **33,583** bytes. This is an illustrative lower-bound fixture: no real histories, locks, FTS, DOM or IPC serialization, and it omits fields the actual display needs. It justifies explicit projections and off-main reads, **not** a safe history size on main. Measure actual structured-clone and renderer costs; splitting SQLite connections alone does not satisfy #616.

### Keep live state on its current channels

Persist projects, indexed sessions/subagents, titles/names, user star/archive/settings, search and historical metrics. Keep busy spinner/turn, running subagent sets, task registry, transcript activity, attention and PTY ownership in memory, on their existing channels. Reconstruct live state from its existing observations after restart; a durable historical subagent row is not evidence that the subagent is running.

The source-derived rates support that boundary: local transcript activity allows one IPC per session per **1 s** (`local-transcript-activity.js:9`), PTY state polls at **3 s** running / **30 s** idle (`public/app.js:1190`), and busy/terminal/task events are event-driven. For ten active sessions, persisting every allowed transcript heartbeat alone could add about **10 writes/s** without a durable-data change; that is a rate envelope, not a measured workload. Durable unchanged files produce **zero** indexing writes; user actions are discrete commands. Persisting each spinner/attention transition would both couple UI liveness to disk and reintroduce unrelated invalidations.

### Startup is stale-while-revalidate

Show the window shell immediately; after schema readiness, fetch settings/working-set records and a readonly display snapshot independently of background indexing. Paint the last durable snapshot with a validating indicator, then stream deltas. Empty or interrupted caches show project placeholders/progress while preserving pending and restored rows. Begin working-set restore as soon as its settings and minimal session lookups are available; never await full snapshot hydration, directory validation, search refresh or a full-scan queue. Keep existing live-elsewhere/continuation guards.

Set an initial engineering budget of **first cached sidebar paint within 500 ms after writer schema readiness** on the agreed warm fixture, and a provisional **250 ms command acknowledgement** target while indexing. These are proposed budgets, not measurements or substitutes for #616's p99 **<30 ms** and no input-hold acceptance. A long one-time schema upgrade displays progress/error on the responsive shell; it cannot be hidden inside a startup main-thread import.

## Consequences

### Migration in four reviewable slices

1. **Connection ownership and lifecycle.** Extract schema/bootstrap and DB access; introduce the writer command protocol, settings mirror and independent readonly queries. Route every write in Study 6164, including file-list FTS and user settings, through it; eliminate main synchronous fallbacks. Initially preserve scan results/behavior inside the writer so the connection cutover is atomic, not a mixed-writer phase. Add migration/rollback-on-crash, lock, writer-error and awaited shutdown tests; run development and packaged native smoke. Keep existing Projects replies during this slice, with reads now pure. No claim that folder replacement or display costs are solved yet.
2. **Incremental sources and consistency.** Add source signatures/content-completeness, changed-only upsert/search/metrics, confirmed missing-ID deletion, live leases and folder progress. Replace global invalidation with scoped checks. Validate warm no-op (zero transcript opens and cache/FTS/metric writes after signature seeding), changed/new/deleted files, unavailable folders, nested subagents, truncation, bridge/continuation dependencies, renames/settings during scans, and restart of an incomplete folder. Bound one or two small fixture runs; larger/live qualification belongs to the scheduled acceptance owner.
3. **Snapshot/delta backend.** Add durable commit sequence, epoch, display projection, coalesced events, replay/resync and chunk acknowledgements. Test subscribe/snapshot races (including `S=10` inside a coalesced `(9,11]` interval), replay/live high-water boundaries, duplicate/out-of-order/lost/partial events, archive-only/settings-only commits, project moves/removal, writer death after commit, and slow-consumer bounds. Keep the old renderer compatible temporarily; avoid enabling both full reload and delta rendering for the same consumer.
4. **Renderer store and acceptance.** Switch startup and ordinary events to the store, patch affected DOM/groups, separate restore from indexing/snapshot hydration, remove obsolete reconciliation/effect and full-reload routes. Test pending/plain terminals, archive/search/SDK/remote/subagent/bridge policies, retained focus and order, and zero full reloads for a single-row change. Capture main p99/max, individual relay/render task time, snapshot bytes/paint, command latency, WAL growth and observed typing with streaming sessions/navigation. Acceptance requires #616's p99 <30 ms **and no observed input hold**; a small probe or a green unit suite alone is insufficient.

**PR #637: close it as superseded; do not merge its current architecture.** Reuse selected source-reading helpers, transition parsing and tests only after checking them against the merged baseline. `workers/index-sessions.js` can inform per-folder job/backfill enumeration but must lose its readonly-effect adapter, whole-folder clearing and global-version retries. `index-effect-batches.js` may inform byte framing; it is not a time bound or the new mutation protocol. Preserve the existing correct watcher transition ordering/ownership and IPC behavior where the supplied review found regressions. Do not carry the appended FTS SQL defect or weakened tests into new slices. This ADR recommends that PR action; it does not perform it.

### Risks and rejected alternatives

| Risk / alternative | Disposition |
| --- | --- |
| Time-sliced main-applied batches | Rejected as the target design: one FTS statement or lock wait is not preemptible, and 50 effects/128 KiB already failed measured latency. May reduce symptoms during an isolated emergency, but cannot establish this ownership contract. |
| Worker owns index writes, main keeps “small” writes | Rejected: two writers still contend and synchronous lock waiting still holds all main IPC. |
| One copied database per reader | Rejected: redundant writes, lagging copies and no shared transaction/version boundary. Multiple readonly **connections** to one WAL DB are the chosen design. |
| In-memory-only index | Rejected: loses stale-while-revalidate startup and makes every restart depend on a full history scan; durable user metadata still needs storage. |
| Poll `data_version` and reload all projects | Rejected for normal updates: no row identities, invalidates on unrelated writes and recreates whole-history/display costs. A full snapshot is a recovery tool. |
| Full atomic folder rebuild | Rejected for ordinary refresh: rewrites unchanged FTS, long transactions, poor command fairness. Commit changed source/dependency units atomically; only disappearance permits bulk folder deletion. |
| Single worker for parsing, writes, search and snapshots | Rejected: full reads/FTS would queue interactive reads behind indexing. Separate read lanes and interruptible parser work are required. |
| Off-main work still saturates CPU/disk | Limit parser concurrency and background throughput; measure typing, reader latency and WAL checkpoints. Moving threads is necessary but not sufficient. |
| Delta projection misses an indirect effect | Include parent/bridge membership, hidden/archive settings and empty projects; parity fixtures compare initial snapshot plus deltas with a fresh readonly projection. Force resync on protocol/version errors. |
| Native crash terminates the Electron process | Worker threads do not isolate native crashes. Packaged smoke and error paths are required; move the writer to a utility process later if observed native crashes justify that extra boundary. |
| Old schema / downgrade / persistence | Additive upgrades preserve user tables. Back up before any future destructive migration; define supported downgrade versions before releasing such migrations. No routine DB replacement. |
| Same-size/mtime rewrite, host-ID collision, unavailable remote | Forced validation for dirty events; explicit deep check for stat collisions; preserve namespace and add collision fixtures; retain cached remote data while unreachable. Do not silently declare missing files. |
| Snapshot lease repeatedly exhausted | Instrument visible size and recovery. Revisit paginated snapshot hydration without blocking restore; never use synchronous main reads as an escape hatch. |

The implementation pays for a command boundary, a renderer store and explicit replay semantics. In exchange, startup and display reads no longer mutate the index, unchanged sessions cost no reparsing/rewriting, and the UI receives bounded changes instead of rebuilding all projects on each notification. All numerical tuning budgets above remain provisional until the four slices produce acceptance evidence.
